## Production route inspection and remaining gap

`pkg/weave/weave_subverbs.go` defines `start --no-spawn` as allocation only.
`runWeaveStart` in `pkg/weave/weave_impl.go` explicitly stores `allocated`, clears
the wrapper PID, and returns without running a worker on that path. Running a
separate local runner afterward does not make weave own or record its outcome.
There is no supported completion/result setter for such an allocated local seat.
The run-500 adapter's fake CLI lifecycle therefore cannot prove production
supervision, and none of those adapters or fake queue tests are brought forward.

The follow-up requested at 20:43 UTC connects the supported
`weave start -- <tool> [args...]` route to a new registered Yoke command,
`lens-script`. Weave owns the process and its result; no local result setter
or direct queue write is needed. The library recorder remains a separate seam.

The JSON task body uses schema `lens-script-task-v1`, with `artifact` (the
CompiledScriptArtifact JSON object, including base64 `script` bytes), `caps`
and `effects` arrays, `help: "script"`, and `no_input: true`. It is bounded to
64 KiB and rejects unknown fields and trailing JSON. `artifact.path` is
informational: execution reads the embedded bytes, never a path. The receiving
entry requires `--digest`, `--caps`, and `--effects`; these must match the body
exactly. It revalidates content identity, literal syntax, and effect authority
before running the in-process interpreter. Missing/empty policies fail closed.
No subprocess, shell, model client or inherited environment reaches the script.

Supported handoff (BODY is the JSON object above; DIGEST is its content digest):

```sh
bashy weave add "bounded local script" --body "$BODY"
bashy weave start --run N --pty always -- /absolute/path/yoke lens-script \
  --digest "$DIGEST" --caps read-only --effects pure
bashy weave status N --json
/absolute/path/yoke lens --since start -t jsonl run:REPO-N
```

Use `--pty always` for captured output: `--pty never` records exit/finish state
but did not create an output log in the actual installed wrapper. Output in the
PTY log has terminal newline normalization; it is not a byte-exact stdout/stderr
archive. The successful read-only run correctly records `no-op`, exit 0, and a
finish time (no commits to submit); a script ending in `false` records `failed`,
exit 1, and its actual output. These are process outcomes, not story acceptance.
Standalone Yoke now registers the existing weave resolver so its run deltas
read the persisted output log. The installed Bashy lens predates that delta
support, so the integration gate uses the newly built Yoke for delta readback.

The isolated end-to-end gate launches the actual built Yoke binary through the
actual installed Bashy wrapper, checks the persisted body, exit/finish/state and
output log, and checks persisted output through run deltas from `--since start` and verifies
that resuming the returned cursor does not replay it. Its
fresh repository/home and allowlisted child environment exclude live agent,
provider credentials, bus/room overrides and production queues. Test code only
reads queue.json; supported weave verbs perform every write. No fake weave CLI
or helper process stands in for the receiving command.
