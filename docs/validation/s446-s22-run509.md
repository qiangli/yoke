## Concrete blocker

The native Go execution boundary does not enforce workspace-only filesystem,
network, or child-executable restrictions. `pkg/weave/weave_isolation.go`
explicitly describes its checkout fingerprint as a detector rather than a fence.
`runWeaveToolPTY` delegates a host process to `agentpty.Run` with resource/time
controls, not a filesystem/network sandbox. The existing local script executor
avoids this issue by interpreting only pure-output builtins and denying both
external execution and file opens. That behavior is unchanged.

This was tested, not inferred solely from comments. The opt-in
`TestS446NativeConfinementProbe` invokes literal `go test -count=1 .` through the
real native PTY runner with a one-minute limit and a fresh temporary module,
home, cache, and workspace. Its environment is explicitly constructed, contains
no provider credentials, and sets GOPROXY=off, GOSUMDB=off, GOTOOLCHAIN=local,
GOWORK=off, GOENV=off, GOTELEMETRY=off and CGO_ENABLED=0, with the requested
GOFLAGS=-p=2 and GOMAXPROCS=4.

The generated Go test successfully:

- wrote `../outside-proof`, outside its workspace but within the test-owned temp root;
- opened and closed a loopback TCP listener (no remote connection or request);
- executed `/usr/bin/true`, a harmless host tool outside a Go-only allowlist.

The parent independently read back the two marker files. The exact diagnostic
verdict is in [confinement.txt](s446-s22-run509/confinement.txt). PASS here means
**the confinement gap was reproduced**, not that confinement or CI/CD passed.
This is a native process-runner probe, not a script assignment or a complete
CI/CD lifecycle acceptance test. It is opt-in because it describes the current
unconfined boundary, not a behavior future confinement must preserve.

Literal argv, an offline Go environment, a private HOME, a cwd, and a timeout
therefore cannot authorize the requested effects. Tests and their init/TestMain
code have process authority; a deterministic repair changes executable code too.
A source allowlist or symlink check alone cannot mediate those syscalls. Digests
identify bytes; they do not constrain their effects.

I stopped before enabling a profile, per the requested stop condition. This is
not a claim that an OS-backed solution is impossible or unavailable on all hosts.
The missing component is an implemented and independently verified execution
backend that confines the Go toolchain **and every descendant**, before launch.
The current native path provides no such contract. A new adapter must deny
network and non-allowlisted tools, restrict reads/writes (including symlinks,
hardlinks and races), isolate compiler/cache/temp effects, handle child cleanup,
and fail closed when the required backend is unavailable. It must not silently
fall back to host execution. No unverified platform sandbox was added here.
